# Benchmarks

Speed and accuracy comparisons between jhin and other torrent release-name
parsers. This directory is a **standalone Go module** — competitor
dependencies live only here and never touch jhin's dependency graph.

[`results/2026-07-24/`](results/2026-07-24/).

### Speed — Go libraries, single-threaded, same corpus round-robin

| Library | per title | B/op | allocs/op |
|---|---|---|---|
| middelink/go-parse-torrent-name | 38.0µs ± 0% | 1.2Ki | 14 |
| razsteinmetz/go-ptn | 43.3µs ± 1% | 2.6Ki | 23 |
| ProfChaos/torrent-name-parser | 60.9µs ± 1% | 0.7Ki | 15 |
| **jhin** | **73.5µs ± 1%** | 4.4Ki | 60 |
| jhin `ParseAll` (batch, 8 threads) | ~19µs/title | — | — |

**jhin is still the slowest of the four per single-threaded call — published
as measured** — but the gap is the trade on display: it runs 424 ordered
handlers extracting 46 fields (behind an Aho-Corasick literal prefilter)
where the others run ~30 regexes filling ~20 scalar fields, and the accuracy
table is what that extra work buys at a ~1.2x speed cost over the nearest
rival. `ParseAll` is jhin's built-in parallel batch API; no competitor ships
one, so that row is jhin-only (any parser can be sharded by the caller).

## Read this before quoting the numbers

- **The gold labels come from Python PTT 1.8.5** (`parser/testdata/golden.json`,
  generated by running the actual Python library). jhin is contract-tested to
  reproduce PTT byte-for-byte, so **jhin's 100% is by construction** — the
  accuracy table's real content is how the other parsers handle the same
  titles. PTT's vocabulary decides ties (e.g. `R5.DVDRip` labels as DVDRip).
- **Normalization is neutral and lives in this harness**, not in jhin:
  `x264`/`H.264`/`AVC` are one codec class, `4K`/`UHD`/`2160p` one
  resolution class, `WEB-DL`/`WEBDL`/`WEB` one source class (WEB-DL vs
  WEBRip stays distinct — that difference is the field's point), titles
  compare case/punctuation-folded. See `canonical.go`; if you think a class
  is unfair, the dump tool prints every disagreement.
- **Scalar-vs-slice**: go-ptn and middelink can only represent one season or
  episode, so multi-season packs count against them. That is a genuine
  capability difference, not a scoring trick.
- Speed numbers are the mean over the full mixed corpus (easy scene names
  and hostile unicode alike), 10 runs through `benchstat`; ± is its reported
  variation. Every library call is wrapped in the same panic guard, so the
  constant defer cost cancels out.
- The npm `parse-torrent-title` (clement-escolano v3) is genuinely faster
  than jhin — published as measured. It extracts a much smaller field
  surface, and no cross-language accuracy score is computed because the
  corpus's gold labels use PTT's schema.

## Reproduce

```sh
cd benchmarks

# accuracy scorecard (markdown)
go run ./cmd/report
# per-title disagreements for one field/library
go run ./cmd/report -field source -lib go-ptn

# Go speed, 10 runs, summarized
go test -run '^$' -bench BenchmarkParse -benchmem -count 10 > speed.txt
benchstat -col /name speed.txt

# cross-language (optional)
cd crosslang
uv venv && uv pip install parsett guessit && npm install
.venv/bin/python bench_ptt.py ../../parser/testdata/golden.json 3
.venv/bin/python bench_guessit.py ../../parser/testdata/golden.json 1
node bench_ptt.js ../../parser/testdata/golden.json 3
```

Competitor versions are pinned in `go.mod` / `crosslang/package.json`.
`TestHarness` keeps the harness itself honest: it fails if any adapter
crashes the run or if jhin scores below 100% on its own contract corpus
(which would mean an adapter or normalizer bug, not a parser change).

`snapshots/` holds jhin-internal microbenchmark baselines (parser prefilter,
rank) that predate this comparison suite.
